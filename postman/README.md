# Postman collection

`restaurant-service.postman_collection.json` covers the public (customer) and merchant
restaurant endpoints, including validation/error cases. Tests are written with `pm.test`,
and ids are chained through collection variables automatically.

## Import

1. Open Postman → **Import** → select `restaurant-service.postman_collection.json`.
2. The collection variable `baseUrl` defaults to `http://localhost:8080/api`.
   Update it if the service runs on another host/port.
3. Run the folders in order, or use the Collection Runner.

## Variables

| Variable | Description |
| --- | --- |
| `baseUrl` | Service base URL including the `/api` prefix |
| `ownerId` | Simulated `X-User-Id` sent to merchant endpoints |
| `restaurantId` | Set automatically by **Merchant → Create restaurant** |
| `activeRestaurantId` | Set automatically by **Public → List restaurants** from the first ACTIVE restaurant |

`uniqueName`, `uniqueEmail`, `uniquePhone` and `updatedName` are generated by pre-request
scripts so the collection can be re-run without duplicate-email/phone conflicts.

## Run with Newman

```bash
npx newman run postman/restaurant-service.postman_collection.json
```

## Notes

- Merchant endpoints take the owner from the `X-User-Id` header (normally injected by the
  API gateway after JWT validation). The collection uses a fixed UUID.
- New restaurants are created with `PENDING_APPROVAL`, so **Public → Get restaurant details**
  uses `activeRestaurantId` from the listing. If the database has no ACTIVE restaurant,
  seed one or activate a created restaurant first.
- **Merchant → Public view of pending restaurant returns 404** verifies that non-ACTIVE
  restaurants are hidden from customers.
- API versioning defaults to `1.0`; no extra headers are needed for these requests.
